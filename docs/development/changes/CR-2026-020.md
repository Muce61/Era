## Trigger

The user approved S2-T11 only on the condition that the existing read-only progress page can
automatically recognize S2-T11 from receipts and validation evidence. If it cannot do so inside the
current Task file scope, implementation must stop and a minimal UI-observability scope amendment
must be submitted instead.

The pre-implementation audit proved that the current progress server and page are specific to
S2-T10:

- the server recognizes exactly six fixed Runtime V2 Foundation/Group-1 Receipt paths;
- the acceptance projection emits only `s2_t10_status`, `group1_status`, and the Stage-3 lock;
- the page renders a fixed S2-T10 task node and reads only the S2-T10 acceptance projection;
- no S2-T11 receipt, validation projection, task registry, or generic Stage-2 task status exists.

Therefore S2-T11 cannot be visible automatically without modifying files outside the current
S2-T11 allowed paths. No path-extraction implementation was started.

## Requested minimal scope

Authorize S2-T11 v1.2 to modify only the following additional observability files:

- `scripts/run_stage2_progress_server.py`;
- `scripts/stage2_progress_ui.html`;
- `tests/scripts/test_stage2_progress_server.py`;
- `tests/research/stage_2/runtime_v2/test_progress.py`.

The existing S2-T11 implementation boundary remains unchanged:

- `src/era100x/research/stage_2/paths/extraction/**`;
- `tests/research/stage_2/paths/extraction/**`;
- S2-T11 validation and minimal append-only audit/receipt evidence;
- `docs/development/TRACEABILITY.md`;
- only S2-T11-direct status and mappings in `docs/development/traceability/rules.yaml`.

## Required design

1. Extend the server with a generic, read-only Stage-2 task projection rather than an S2-T11-only
   PASS constant.
2. Derive S2-T11 state from append-only path-extraction receipt and validation facts. Missing,
   malformed, contradictory, partial, or failed evidence must never produce PASS.
3. Preserve the existing S2-T10 projection and all 61,776-partition acceptance checks unchanged.
4. Render the active Stage-2 Task from API data. Raw HTML must default to CHECKING and must not
   predeclare S2-T11 PASS.
5. Keep Stage 3 locked regardless of S2-T11 state. The amendment cannot approve S2-T12 or any
   later Task.
6. Keep the page read-only. It may not start, resume, stop, publish, mutate, delete, or clean any
   research execution.

## Acceptance tests

- missing S2-T11 evidence renders `NOT_STARTED` or `CHECKING`, never PASS;
- a valid in-progress receipt renders `IN_PROGRESS` with live counters;
- a terminal failed receipt renders `FAILED` and exposes its auditable reason;
- PASS requires the complete S2-T11 receipt, full-output validation result, input/output hashes,
  BTC/ETH separation, and every registered acceptance check to pass;
- malformed, symlinked, conflicting, or non-append-only evidence fails closed;
- S2-T10 remains `PASSED` with 61,776/61,776 exact matches and zero differences;
- S2-T11 status is rendered from the API without a hard-coded PASSED value;
- Stage 3 remains `LOCKED`;
- directed UI/server tests and the complete repository quality gate pass;
- browser inspection confirms the live page and console are clean.

## Explicit non-goals

This Change Request does not implement path extraction, change H1/H2 ordering, define path labels,
run full data, alter Stage 1, rewrite existing Run evidence, execute S2-T12 through S2-T20, or
unlock Stage 3. It only requests the minimum additional files needed to make S2-T11 observable.

## Decision required

Muce explicitly approved this bounded observability scope. Implementation may change only the
four listed UI/server files, must remain read-only and cannot promote S2-T11 without complete
append-only full-output evidence.
