## Decision

Muce approved the current formal deterministic pair as:

- Run A: the complete legacy generator output released through CR-2026-006;
- Run B: a fresh V2 full reconstruction from the frozen Stage 1 inputs, first building the shared
  Feature Foundation and then recomputing all Group-1 event outputs.

This approval does not cancel or sample the current full reconstruction. Run B must consume the
entire approved Stage 1 period and independently produce every BTC/ETH, V1_PRICE/V1_FLOW and
parameter-set result. The implementation and physical layouts may differ; research semantics may
not.

## Layout-independent semantic comparison

Physical path, file count, Parquet byte hash, compression metadata and execution timestamp may
differ. Each run must independently validate those physical facts. Cross-run acceptance instead
uses a canonical owner-day projection:

```text
schema_name
+ instrument
+ variant
+ UTC owner date
+ canonical rows sorted by the schema's stable key and canonical serialization
```

For every dataset and owner date, comparison must prove identical:

- row count and empty/non-empty state;
- canonical-record logical hash;
- ID set and, where applicable, ID multiset hash;
- canonical payload hash association;
- ownership and inclusion status;
- Primary/Exploratory, T1-T4, parameter-set and reason distributions.

The final dataset semantic hash is an aggregate of the ordered owner-date receipts and explicitly
excludes physical paths. An existing Catalog aggregate that includes relative paths is not a valid
cross-layout semantic hash. Any row, ID, payload, count or distribution mismatch is `FAIL`; no
tolerance, sampling or manual record selection is allowed.

## Current Group-1 acceptance

S2-T10 v1.8 passes only when Run A is formally published with Quality PASS, the complete Feature
Foundation and fresh Run B are published with Quality PASS, and the full layout-independent
comparison passes. A failed or missing Run A cannot be rescued by Run B, and a V2 result cannot be
compared against the old staging tree as if it were a formal publication.

As amended by approved CR-2026-009, `compare` is a mutating evidence command only in the narrow
sense that it writes one append-only deterministic comparison report. It must perform the same
write probe and acquire the same run lock as other mutating commands; it may not alter Catalog,
data, receipts, manifests or publication state.

## Future deterministic tiers

The following protocol applies only to future event work that receives its own approved Task and
preregistration. It does not approve any new event now.

### Tier F — Feature Foundation

The initial Foundation, a Stage 1 baseline change, or a primitive/schema/availability change
requires a complete authoritative source build and independent Foundation determinism evidence.
The changed Foundation invalidates every dependent event, path, label and statistic.

### Tier E — Event definition over a frozen snapshot

When all required fields already exist in an immutable validated Feature Snapshot, two independent
event runs must fully reconstruct that event from the same snapshot. They must not rescan raw Stage
1 Trades merely to recompute already published feature facts.

### Tier D — Appended or dirty partitions

For unchanged definitions over new dates or a bounded dirty set, two independent computations of
the affected partitions plus their maximum causal halo are required. Sealed historical partitions
outside the invalidation closure are not rebuilt.

If a future event needs a primitive absent from the Foundation, the run is `BLOCKED` until a
separately approved feature extension builds and validates that primitive once. A one-second
aggregate may not be represented as exact H2 trade order, and missing Bid/Ask/L2/latency/execution
facts remain unavailable.

## Invalidation

Any change to semantic serialization, stable keys, owner-date rules, feature formula or
availability, evidence capability, event identity, Stage 1 authority, preregistration, parameters,
labels, matching, metrics or tier rules invalidates the affected comparison evidence. Old reports
remain append-only.

## Validation scope

- canonical serialization and stable-key tests;
- daily receipt and final semantic-hash permutation tests;
- cross-layout equivalence and intentional mismatch tests;
- full Run-A/Run-B ID, payload, count and distribution comparison;
- Feature Snapshot reuse proof and raw-Trades access prohibition for Tier E;
- invalidation-closure and halo tests;
- explicit BLOCKED tests for missing capability.
