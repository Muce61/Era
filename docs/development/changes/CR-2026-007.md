## Discovery and decision

The approved CR-2026-006 release child is already performing the single deep scan of the fixed
9,508/9,508 source Run A. Stopping that child would discard useful progress, while allowing its
legacy parent to create another daily-file Run B would repeat the same raw Trades scans and
small-file publication cost. Muce approved a hybrid cut-over:

1. The current Run A release child remains authorized and, if it passes quality and atomic
   publication, remains the formal Group-1 Run A.
2. The legacy CR-2026-006 parent is paused and must not create a legacy Run B.
3. S2-T10 v1.8 builds a shared, immutable Feature Foundation from the frozen Stage 1 input and
   performs a fresh full Group-1 reconstruction as Run B.
4. Run B reuses no Run A staging, published data, sealed shard or intermediate artifact.
5. Run A and Run B are accepted only through the exact semantic protocol approved by
   [CR-2026-008](CR-2026-008.md).

This is the bounded corrective route to complete S2-T10. The former requirement to finish Group 1
before implementing a reusable platform is waived only for S2-T10 v1.8. It does not authorize
S2-T11 through S2-T20, a second event setup, a new strategy family or a research conclusion.

## V2 contracts

The V2 platform may introduce the following independently versioned, append-only contracts:

- `FeatureDefinition` and `FeatureSnapshot`, including causal availability, source capability,
  schema hash, code-tree hash and source logical hashes;
- `FeatureFoundationManifest`, including all Stage 1 authorities, feature definitions, physical
  partitions, logical partitions, quality facts and invalidation rules;
- an explicit fail-closed Research Setup / Context / Variant registry;
- a content-addressed build node and dependency key;
- partition receipts containing owner-date row counts, semantic hashes, identity hashes, quality
  facts and terminal state;
- a layout-independent Catalog that separates canonical semantic hashes from Parquet paths and
  byte hashes;
- a Group-1 compatibility projection that reconstructs the currently approved daily semantics
  from V2 physical files.

The V2 implementation root is `src/era100x/research/stage_2/runtime_v2/` with the fixed external
entry point `scripts/run_stage2_research.py`. S2-T10 v1.8 freezes its approved command surface to
`{preflight,build-foundation,run-group1,resume,verify,compare}`; no unregistered event or ad-hoc
threshold may be supplied through the CLI.

The V2 engine may use larger physical shards and Catalog-only empty partitions. Logical ownership
remains the Episode or fact's approved UTC owner date. Physical compaction must not merge BTC and
ETH, V1_PRICE and V1_FLOW, Primary and Exploratory, or different parameter sets semantically.

## Approved setup boundary

Only the existing `KEY_LOW_SWEEP_RECLAIM_HOLD_V1` setup, `CAUSAL_EMA20_1H` context and registered
V1_PRICE/V1_FLOW variants may be executed. Registry conformance infrastructure may support future
plugins, but unknown, test-only or unapproved definitions fail closed. The following remain
unchanged:

- all CanonicalKeyLevel, Sweep, Reclaim, Hold, Trigger and Flow formulas;
- T1 through T4 and all 20 parameter sets;
- canonical candidate identity and semantic payload projection;
- the FROZEN `market_episode_id` and consumption semantics;
- Stage 1, preregistration and config hashes;
- historical H1/H2 field and evidence boundaries.

## Run A protection

The source Run A remains owned by CR-2026-006 until its release child reaches a terminal state.
CR-2026-007 must not change its Execution Manifest, release supplement, checkpoint, progress,
sealed shards, staging, reports or published tree. The paused parent may not be resumed and may not
create Run B. If Run A fails, its failure remains append-only and S2-T10 stops; a one-sided V2 Run B
cannot satisfy acceptance.

If Run A succeeds, CR-2026-006 may be resolved for the Run-A release-recovery scope. Its legacy
Run-B orchestration is superseded by CR-2026-007 and CR-2026-008, but the successful Run A is not
invalidated.

## Run B and compatibility projection

Run B must use a new run ID and a new locked V2 Execution Manifest. Its phases are:

1. build and validate the complete Feature Foundation from Stage 1 published inputs;
2. publish the Foundation append-only;
3. reconstruct the complete Group-1 event chain from the Foundation;
4. materialize a compatibility projection for every approved Group-1 dataset and UTC owner day;
5. pass V2 quality, atomic publication and recovery checks;
6. compare the full semantic projection with formal Run A under CR-2026-008.

The compatibility projection must reproduce the same canonical records even when V2 uses fewer or
larger physical Parquet files. It may not delete empty logical partitions, silently normalize
payload fields or pool variants.

## Invalidation and failure

Feature source/schema/formula/availability, Stage 1 authority, event semantics, identity,
preregistration or config changes invalidate affected nodes and every dependent output. A node is
reusable only when its full content key and Manifest authority match. Missing capability,
unregistered setup, mixed evidence, identity conflict, UNKNOWN, receipt mismatch or semantic
comparison mismatch is a hard failure and blocks publication or acceptance.
